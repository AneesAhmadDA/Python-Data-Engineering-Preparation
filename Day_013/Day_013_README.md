# 1. Python — Logging in an ETL Pipeline

## Objective

Replace diagnostic `print()` statements in the ETL workflow with Python's built-in `logging` module. The logger is configured to send messages to both the console and a persistent log file.

## Pipeline stages

- **Extraction:** Read the grocery-sales CSV and record the source path, row count, and column count.
- **Transformation:** Inspect the data, identify duplicate transaction IDs, remove duplicates using the existing `keep="first"` rule, inspect missing values, and impute missing numeric values with their column means.
- **Loading:** Save the transformed DataFrame to `Cleaned_data.csv` without writing the DataFrame index.

## Logging configuration

The implementation uses:

| Logging level | Intended use in this pipeline |
|---|---|
| `INFO` | Pipeline start/end, extraction and loading progress, row counts, and successful validation steps |
| `WARNING` | Duplicate transaction IDs and missing values requiring attention |
| `ERROR` | A failed pipeline execution |

Two handlers are configured:

- `logging.StreamHandler` sends log messages to the terminal.
- `logging.FileHandler` writes log messages to `Python/logs/etl_pipeline.log`.

The log format includes a timestamp, severity level, logger name, and message. When an exception reaches the pipeline coordinator, `logger.exception()` records the error and traceback before the exception is re-raised.

# 2. SQL — CTEs and Window Functions

## Objective

Build a readable, two-stage SQL query that calculates total sales per product and ranks products independently within each category.

**Database:** `Internship_prep`  
**Tables:** `dim.products` and `fact.sales`  
**Join key:** `product_id`

## Query implementation

```sql
USE Internship_prep;

WITH ProductSales AS (
    SELECT
        d.product_id,
        d.product_name,
        d.category,
        SUM(fs.total_amount) AS Total_sales
    FROM dim.products AS d
    LEFT JOIN fact.sales AS fs
        ON d.product_id = fs.product_id
    GROUP BY
        d.product_id,
        d.product_name,
        d.category
),
Rank_CTE AS (
    SELECT
        *,
        ROW_NUMBER() OVER (
            PARTITION BY category
            ORDER BY Total_sales DESC
        ) AS row_num,
        RANK() OVER (
            PARTITION BY category
            ORDER BY Total_sales DESC
        ) AS [Rank],
        DENSE_RANK() OVER (
            PARTITION BY category
            ORDER BY Total_sales DESC
        ) AS Dense_Rank
    FROM ProductSales
)
SELECT *
FROM Rank_CTE;
```

## How the query works

### CTE 1 — `ProductSales`

The first CTE joins products to sales and groups the matching records by product ID, product name, and category. `SUM(fs.total_amount)` calculates the total sales value for each product.

A `LEFT JOIN` is used so that products are retained even when they have no matching sales rows. For a product with no matching sales, `SUM()` can return `NULL`.

### CTE 2 — `Rank_CTE`

The second CTE reads the aggregated output from `ProductSales` and calculates three rankings. Each window function uses `PARTITION BY category`, so ranking restarts for every category. The ordering is based on total sales in descending order.

| Function | Behaviour |
|---|---|
| `ROW_NUMBER()` | Assigns a unique sequential number to each row in a category, including rows with equal sales values. |
| `RANK()` | Assigns equal ranks to tied values and leaves a gap after a tie. |
| `DENSE_RANK()` | Assigns equal ranks to tied values without leaving a gap after a tie. |

## SQL observations and limitations

1. **Tie behaviour:** The Accessories category demonstrates that tied sales values receive the same `RANK()` and `DENSE_RANK()` value. This particular output does not show the gap distinction between those two functions because there is no lower, third distinct sales value after the tie group. A separate controlled test with another lower-valued product would make the gap difference visible.
2. **`ROW_NUMBER()` tie order:** The query orders each window only by `Total_sales DESC`. When products tie, their relative `ROW_NUMBER()` order is not guaranteed. To make row numbering deterministic, add a unique tie-breaker such as `product_id` to the `ROW_NUMBER()` ordering. Keep the `RANK()` and `DENSE_RANK()` ordering based on `Total_sales` alone when equal sales should remain tied.
3. **CTE performance:** A CTE improves query organization and readability, but using a CTE does not automatically make a query faster or guarantee that SQL Server materializes the CTE as a separate stored result. Performance should be assessed using the execution plan and measurements.
4. **No top-three filter:** The submitted query returns the rankings for all products. It does not yet filter the results to the top three rows or ranks in each category.
